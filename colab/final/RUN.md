# Formal Spark multimodal Colab campaign

Use `colab/Spark_Formal_Full_Finetune.ipynb` from [BaiTian6641/Spark-X2.6-VL](https://github.com/BaiTian6641/Spark-X2.6-VL). The small notebook downloads a source-only runtime ZIP from an immutable GitHub commit and verifies its SHA256 and exact file inventory before execution. Sources, dependency locks, the upstream vision-source archive and the runtime ZIP are in that repository. There is no embedded base64 payload. It does not depend on this workstation or upload its old checkpoints. The pipeline is implemented; the complete native CUDA campaign has **not** been run or certified by the CPU tests shipped with it.

## Current formal script and storage policy

The final notebook runs the complete staged curriculum: bridge alignment, full vision tuning, full temporal/AV tuning, full speech/sound understanding, full speech/sound generation, joint full tuning, two instructor-controlled replay comparisons, protected evaluation, offline export reload and final HF upload. The main stages update all Spark parameters. This is the multimodal prototype campaign, with no reduction to an image-only trial.

The latest user instruction changes full checkpoint storage to **Hugging Face**. Google Drive remains cold storage for small receipts, reports and instructor accounting. This storage section supersedes the earlier Drive-checkpoint design in the historical campaign documents.

| Artifact | Destination |
|---|---|
| Existing pinned data | `datasets/TassP0lar/SparkX2.6-MM` |
| Full resumable snapshots | Private model repo `TassP0lar/SparkX2.6-MM-checkpoints` |
| Finished inference package | Private model repo `TassP0lar/SparkX2.6-MM` |
| Small receipts, reports and ledger | Configured cold Drive project, within its 2 TB cap |

`HF_TOKEN` needs read access to the component models and write access to **both private model repositories**. No token is placed in a cell, file, argv or checkpoint. CPU preflight initializes or verifies the small checkpoint repository identity before expensive training. The dataset repository is not modified by this notebook.

On a roughly230GB VM, the rolling media cache is23GB, the free floor44GB, and the initial full-checkpoint reservation55GB per slot. Two local snapshots may coexist during saving/upload. Every payload file is verified against the exact HF commit (LFS SHA256 for large objects, downloaded content SHA256 for ordinary small Git files). After the exact-revision receipt has also been backed up to Drive, only the newest local snapshot remains. Older verified local checkpoints are automatically purged. Upload, hash, quota or receipt-backup failures preserve the fallback and the new local checkpoint; they stop training rather than delete an unverified artifact.

The remote `checkpoint/` directory is updated atomically. Old exact revisions remain in HF Git history for recovery and parent/candidate/control RSI. **Local purge does not reclaim HF history quota.** The script never squashes remote history or deletes unrelated files. Ensure the HF account has sufficient private storage; the program stops if the Hub rejects a write. Source model files, the active bounded shard cache, the newest checkpoint, original workstation checkpoints and unrelated data are not part of checkpoint cleanup.

Open on CPU and run the setup cells in order. Next, choose G4, enter the current balance/rate, enable CUDA setup and run qualification once. On the fresh VM, repeat setup and use `RUN_MODE='train'` with the qualification profile receipt; later sessions use `RUN_MODE='resume'` plus the exact HF checkpoint receipt. Opening the notebook or leaving `RUN_MODE='inspect'` performs no training. Actual full-model GPU qualification and fresh-VM recovery remain runtime checks, not claims already established by this script release.

## Repairing the earlier CPU setup failure

The earlier notebook used system `venv(..., with_pip=True)`, which failed in Colab's `ensurepip` subprocess. Its traceback did not include the subprocess output, so it does not establish why `ensurepip` failed. It can leave an isolated Python executable with no pip, and the old setup incorrectly treated that executable as a complete environment.

Open the new GitHub-backed notebook and run source bootstrap, configuration, authentication/Secrets and CPU setup in order. Keep the same `/content/spark-formal` work root and Drive folder. The new setup validates and adopts the earlier isolated `env-cpu`, synchronizes the complete hashed CPU lock and records readiness only after `pip check` succeeds. It also repairs the equivalent CUDA environment if needed. It never clears an environment directory or deletes cached data, checkpoints or Drive files. An unexpected directory or a Python version other than3.13 stops setup without deleting it.

The standard-library bootstrap downloads the pinned `uv0.13.5` Linux x86_64 wheel from PyPI, checks the wheel's size/SHA256, extracts only its separately hash-pinned executable and creates a pipless virtual environment. `uv pip sync` installs every package from the hash-locked requirements, including `pip26.2.2`; system `ensurepip`, kernel pip and unpinned `get-pip.py` are unnecessary. On repeat, sync audits the existing installation instead of reinstalling matching packages. A failed retry invalidates the previous readiness receipt. Setup serializes environment changes with a local lock and preserves the44GB free floor. CUDA package selection uses `--torch-backend cu130`, which routes PyTorch packages to their index while leaving unrelated packages on PyPI.

The source path includes the verified runtime hash, so it can coexist with the earlier extracted source. This is a new source binding for future formal checkpoints; it must not be represented as an identical-source continuation of an older trained campaign. The reported failure occurred before the new formal campaign's training setup.

## Campaign operation

### If CPU setup succeeds but the campaign stops

`environment_setup_complete` proves that package installation passed. It does not prove model access, dataset validation or Drive readiness. The launcher now captures both child stdout and stderr into notebook output, including the exact `stopped` event, exit code and recovery action. Bounded, sanitized per-invocation logs are saved under `/content/spark-formal/logs`. Credentials, bearer values and signed URL queries are removed before display or logging. Ctrl-C signals the runner once and drains its remaining output while it saves; inspect the actual committed receipt before calling a checkpoint resumable.

The observed 2026-10-27 CPU failure was **HTTP403 `GatedRepo` from Hugging Face**, with the correct publishing account and a fine-grained token. Stable Audio model access had not been granted. The user subsequently completed its access form; a read-only Colab metadata probe then succeeded with the same token. This was separate from the earlier `ensurepip` installation failure.

Continuing the same Colab preflight exposed a second failure: the CPU lock omitted `Jinja2`, needed by Transformers `apply_chat_template` during the corpus audit. The CPU input/lock now explicitly include `Jinja2==3.1.6` and `MarkupSafe==3.0.4`, using the same versions/hashes as the existing CUDA lock. Other package versions are unchanged. The real isolated-CPU installation test now tokenizes a chat template through Transformers, so a working import or `pip check` alone cannot miss this optional runtime dependency.

If this happens in another account, review/request access on the [Stable Audio Open1.0 page](https://huggingface.co/stabilityai/stable-audio-open-1.0), using the same account that owns `HF_TOKEN`. The form accepts the model license and shares the submitted contact details with the model owner. Once access is granted, ensure a fine-grained token permits reading this gated model and rerun CPU preflight in the same VM. Do not paste the token into code. The runtime does not accept terms or broaden token scope. It checks the pinned file's Hub metadata without following a signed CDN HEAD redirect; access denial, transport failure and metadata mismatch produce different errors. Successful metadata access does not establish download throughput or publication write permission.

Progress events identify model metadata, dataset/split preparation, full-corpus context audit and Drive cold storage. A failed retry invalidates any previous successful local preflight receipt, and GPU commands require a successful receipt for the current source release. No GPU training or instructor call occurs in this preflight.

### Running the campaign

1. Open the notebook in Colab with a **CPU runtime first**. Enable notebook access to the Secrets named `HF_TOKEN` and `OPENCODE_API_KEY`. The HF token needs read access to the original models and write access to the private checkpoint and final **model** repositories. The dataset repository of the same name is a separate namespace.
2. Obtain access to [Stable Audio Open 1.0](https://huggingface.co/stabilityai/stable-audio-open-1.0) with that HF account after reviewing its terms. The program checks access and never accepts terms automatically. This replaces the earlier Small candidate: its tools pin an incompatible Python/Torch environment, and its 11-second limit would crop the released sound/music targets. The Diffusers path supports the complete clips used here.
3. Review the configuration, Drive folder and instructor route eligibility. `instructor_route_eligibility_receipt` must contain provider `OpenCode Go`, model `mimo-v2.6-pro`, endpoint `https://opencode.ai/inference/go/openai/v1/chat/completions`, `permits_dataset_review: true`, an `evidence_url` and `checked_at`. Populate it from provider/account evidence, not an invented approval. Prior endpoint readiness does not establish eligibility for dataset review. The notebook can do CPU preflight and CUDA qualification while this is pending; the long formal campaign requires it.
4. Run CPU setup/preflight and Google authentication. Mounting `/content/drive` is optional and never changes the active work root. Dataset metadata, model preprocessing/configuration, full-corpus task roles, source splits, text lengths and gated access are checked before GPU use. No instructor calls occur in CPU preflight.
5. Select the reviewed G4 Blackwell GPU, enter the **currently displayed CU balance and CU/hour rate**, install the separate hashed CUDA environment and run `qualify`. This builds every real branch, performs five warm-up and 30 timed full updates for each family, checks actual gradients and parameter changes, measures complete optimizer checkpoints and predicts the configured curriculum cost. It also performs a real mixed update through the actual Studio SFT loop, commits full snapshots to HF and backs up their small receipts to Drive. A resolved dependency lock is not a qualification PASS. Qualification and recovery alone do not require instructor API calls.
6. Save the emitted profile/checkpoint receipts, reconnect a **fresh VM**, repeat CPU setup, enter fresh usage observations and run `train` with the profile receipt. The program restores the complete qualification snapshot, reproduces two native continuation updates, and compares losses/parameter samples against the saved oracle. It then restores the original initial snapshot. This one recovery qualification is intentional; it protects a campaign spanning ephemeral sessions. Same-VM/new-process checks do not pass this gate.
7. The formal stages then run through Studio's actual headless backend. Full Spark parameters train in every principal stage. Only the short declared bridge alignment freezes the pretrained networks. Codec/autoencoder infrastructure stays frozen. Microbatch is one; accumulation is eight; parameter storage is FP32 with BF16 automatic mixed precision and AdamW8bit. There is no LoRA or quantization fallback. Principal stages have explicit fresh optimizer/cosine warm-up schedules; in-stage resume restores exact optimizer state. Both RSI arms inherit the same parent optimizer moments and use the same fresh schedule. Spark is loaded through its declared eager interface and a tested PyTorch SDPA kernel adapter preserves the original masks, RoPE, cache positions and output gates. FP32 forward/backward parity is checked against the pinned decoder source; complete CUDA parity remains a runtime gate. Custom Spark throughput is measured by qualification.
8. If the projected complete curriculum exceeds the authorized CU envelope, execution stops before formal training. A budget stop, OOM, failed recovery or incomplete stage cannot be labeled completed. Change the reviewed campaign/budget explicitly if profiling shows that one campaign cannot fit. Refresh the balance/rate observation at least every 12 hours. A new paid session may be needed; Colab connection lifetime is not guaranteed.
9. On interruption, choose `resume` and an exact verified HF checkpoint receipt. The loader restores weights, optimizer, scheduler, RNG, stage, frozen source split and optimizer-committed data cursor. Issued but uncommitted prefetched records replay. An uncertain instructor POST is reconciled through durable intents and is never retried automatically. If the failure was checkpoint upload, first use the notebook's CPU-only `upload-checkpoint` retry cell for that closed directory. It performs no optimizer steps, verifies/reconciles the exact transaction and then permits local cleanup. Do not run it concurrently with training.
10. When all stages and two controlled instructed-RSI rounds finish, the protected audit and native samples run. The selected completed package is reloaded offline from its export, then uploaded to the configured private model repository (default `TassP0lar/SparkX2.6-MM`) using the in-memory HF token. The remote weights' LFS SHA256 is checked and the commit receipt is committed to Drive. Optimizer state, credentials, raw training media and instructor request ledgers are excluded from the model upload.

## Storage and recovery

The source media stay at dataset commit `f472f980a6c95d3e9844f27e6045c8c09b21536a`. A separate pinned metadata companion enumerates every variant and exact TAR member. No full Git LFS clone or full Hugging Face dataset cache is made in Colab. Each of ten component caches is capped at 2.3 decimal GB, for a total 23 GB. There is no background unbounded prefetch or Drive random I/O. Member bytes are read under protected TAR leases. Metadata is in a local SQLite database.

The runtime preserves a44 decimal GB local free floor and reserves two measured complete checkpoint slots. The initial per-slot reservation is55GB until measured; a larger snapshot fails the profile. Pretrained source downloads and HF checkpoint restores are direct revision-and-content-verified files, with no extra Hub snapshot cache copy. Closed exports hardlink immutable local weights to avoid another full staging copy. Only an older, campaign-owned local snapshot with a verified remote acknowledgement can be reclaimed. After each verified new upload, the newest local snapshot is retained. Restoring an older revision for RSI also keeps a verified local fallback until restoration finishes; preprocessors/codecs are rebound to the retained directory before cleanup. Unknown/uncommitted local directories stop cleanup. No workstation checkpoint or unrelated cache is deleted. Small Drive artifacts remain immutable within the2TB project cap. The90-minute checkpoint target can increase to account for measured upload overhead, up to the declared180-minute maximum; a larger requirement stops the run. After full optimizer qualification, local slots use measured size plus10% instead of the provisional55GB bound.

Keep the complete emitted profile and checkpoint receipts outside the VM (notebook output and cold Drive indexes suffice). HF checkpoint receipts contain `repo_id`, immutable `revision`, `marker_path` and `commit_sha256`; Drive profile/report receipts contain `commit_file_id` and `commit_sha256`. The notebook's `discover` action lists cold artifacts and the latest verified HF checkpoint. HF payloads and `COMMITTED.json` land in one atomic commit, followed by independent remote verification. An interrupted or unverified upload is not a resumable checkpoint acknowledgement. The manifest records every file's bytes and SHA256, including optimizer/scheduler/RNG and source split/cursor state. Credentials and upload transport state stay private to the VM and are not copied into snapshots.

## Data and evaluation

All 304,861 original instructions are enumerated. Long MusicNet note targets are converted into complete, ordered 24-event questions, producing 315,359 training/evaluation views before splitting. Every note is retained; the full 15-second waveform is retained. These extra views do not represent new recordings. Known source groups, declared speaker/book/work/session keys, shared OCR/text articles, known Flickr identities and exact whole-media sets are connected before deterministic splitting. Every available family/language has independent train/dev/promotion/audit support; exact counts and independent-group counts are frozen in `corpus.report.json`. Small group counts limit statistical power. Original upstream evaluation sets stay excluded; unknown pretraining overlap remains unknown.

Generation waveform targets never enter recognition encoders or the Spark conditioning prefix. TTS uses only text present in the request and a learned default voice; target-speaker encoders are absent. Whisper handles speech; CLAP handles general sound. Explicit absolute waveform clocks enter the temporal resamplers, so chunk order is represented; repeated frontend padding is excluded from the declared valid feature duration. CLAP uses ordinary autograd because this pinned Transformers class does not advertise gradient-checkpoint support. The video route preserves actual presentation timestamps and represents unknown capture clocks explicitly. NASA full-source GMT context is not assigned to trimmed derivative frames. NaFlex uses real spatial grids, thumbnail/detail tiles and spatial 2x2 feature concatenation with original-image coordinate mapping. Motion uses the pinned V-JEPA2.1 base encoder with an explicit 16-frame adaptation from its native64-frame configuration, averaging its four hierarchical features; the unused image-only stem is removed.

Native speech uses the pretrained Qwen3-TTS talker with manual causal first-codebook supervision plus its real sub-talker loss. Sound/music uses the pretrained Stable Audio DiT with the native v-prediction objective and a differentiable Spark-state bridge. Both objectives must reach Spark and show real parameter writeback. This is a composite native prototype, not a claim that Spark was pretrained as an omni model. `spoken_answer` composes Spark text decoding with the included native speech head conditioned on Spark media/context states; no external TTS service is used. The corpus does not contain paired spoken audiovisual-dialogue answers, so that composition needs separate evaluation and is not a trained interleaved omni-dialogue claim.

The main corpus trains each declared complete epoch plus declared retention replay. The training objective balances family/language strata by inverse frequency with an explicit5x loss-weight cap while still consuming every declared record. Raw per-stratum losses are reported separately from the weighted optimizer loss. Both RSI arms use the same control-derived weights, so the instructor comparison does not change its weighting policy between arms. Instructor RSI is two **small controlled replay experiments** under the $50 cumulative ceiling. A larger MiMo model sees training media and real student outputs, recommends replay priority, and never changes trusted waveform/geometry/transcript targets. Each candidate is compared with uniform replay from the same parent, pool, number of examples and updates. Promotion uses fixed source-held-out strata and regressions; rejected candidates are retained as evidence and are not relabeled improvements. This implements instructed iterative improvement, not autonomous weight editing, nested learning or architecture mutation.

Reports separate per-family losses, limited native text/audio samples, image/audio ablation and video-order reversal. Text decoding uses fixed task budgets (1024 tokens for full OCR/score views,512 for long captions/tracks,256 otherwise) rather than an answer-length oracle or a universal128-token cap. Cross-family loss scales are not combined into one training-quality score. Audio listening, intelligibility/tone quality, prompt matching, music quality, robust spatial/video reasoning and public benchmark results remain explicit acceptance work. The private trained package can be stored before human acceptance, but its card must not claim those capabilities passed. This release does not promise that the available narrow music/AV/time-lapse sources are sufficient for broad competence.
